# Backend 4.1

Текущий MVP — обычные личные и групповые чаты с историей на сервере. Секретные чаты, E2EE и федерация не реализованы. Один процесс приложения: SQLite WAL и локальные очереди WebSocket.

## Где добавлять изменения

| Модуль | Ответственность |
| --- | --- |
| `Features/Accounts` | Пароли, регистрация, сессии, авторизация HTTP и WS |
| `Features/Profiles` | Профиль, поиск, аватары |
| `Features/Chats` | Чаты, участники, роли, атомарное создание и передача владения |
| `Features/Messages` | Сообщения, история, идемпотентность, прочтения, удаление |
| `Features/Reactions` | Маршруты и контракты реакций |
| `Features/Attachments` | Вложения, файловое хранение и проверка изображений |
| `Features/Realtime` | Подписки, ограниченные очереди, отзыв и очистка сессий |
| `Infrastructure` | Соединения SQLite, запуск миграций, шифрование, OpenAPI |
| `Core` | Сборка приложения и общий формат ошибок |

DTO и строки БД лежат рядом с соответствующей функциональностью. Namespace существующих типов сохранён для минимального изменения вызовов. `ChatRepository` и `MessageRepository` содержат SQL и правила доступа, общие для HTTP и WebSocket. Это небольшой модульный монолит, без ORM, универсального бизнес-репозитория или инфраструктуры распределённых событий.

Новая таблица/колонка: добавьте в свой модуль новый `ISchemaMigration` с уникальным сортируемым `Id`, например `005_messages_delivery`. Миграции автоматически обнаруживаются в сборке, выполняются по порядку в `BEGIN IMMEDIATE` и записываются в `schema_migrations` после успешного выполнения. Существующие миграции после релиза не редактировать. Ошибки больше не маскируются под «колонка уже существует». Старые данные сохраняются. `Infrastructure/Db.cs` менять для каждой фичи не требуется: там только соединения, WAL и сериализация записей.

Многострочные изменения выполняйте через `SchemaMigrator.Transaction` внутри `Db.Write`. Не публикуйте события внутри транзакции. Сохранение предшествует событию; сбой асинхронной рассылки не меняет успешный ответ. HTTP и WS используют одинаковые проверки членства. Повтор отправки использует `client_ref` отправителя и неизменяемый защищённый отпечаток исходного содержимого.

## Защита данных

Текст сообщений и bio шифруются ASP.NET Core Data Protection; файлы — отдельным purpose. Используются аутентифицированные шифрованные payload, постоянное хранилище ключей и автоматическая ротация. Не пишите текст сообщения напрямую SQL-запросом: операции `MessageRepository.Send` и правка сообщения защищают значение перед сохранением, а `MessageRow.Text` расшифровывает его при чтении. `storage_version` отличает старые строки от защищённых. Отпечатки идемпотентности тоже зашифрованы, чтобы дамп БД не позволял подбирать короткие тексты по SHA-256.

На первом запуске мигрируются существующие строки и файлы; замена каждого файла атомарна, миграция возобновляется после прерывания. `secure_delete`, checkpoint WAL и VACUUM убирают прежний открытый текст из свободных страниц текущей БД. Удаление «у всех» стирает текст, отзывает вложения и реакции. Резервные копии до миграции остаются чувствительными данными.

`MESSENGER_KEYS` — постоянный каталог ключей **вне каталога БД и файлов**. На Linux каталог доступен только владельцу (0700). На сервере это `/var/lib/messenger-keys`; у сервиса отдельный системный пользователь. XML ключей не шифруется дополнительным мастер-ключом: безопасность опирается на права ОС. Копия одной БД или каталога файлов не содержит ключей, но полный доступ к серверу/его резервной копии позволяет расшифровать данные. Для более строгой модели нужен внешний KMS/сертификат; это не E2EE. Публичные метаданные (имена, теги, названия чатов, размеры/имена вложений, связи и время) остаются открытыми. Секреты не должны попадать в Git.

Не удаляйте старые ключи после ротации. Резервируйте каталог ключей отдельно с ограниченным доступом и проверяйте восстановление вместе с БД и файлами. Потеря ключей останавливает запуск по проверочному зашифрованному значению; приложение не начинает создавать несовместимые данные молча. Старый бинарник не умеет читать новый формат, поэтому откат после миграции требует **согласованной** копии старого приложения, БД и файлов.

Пароли: PBKDF2-SHA256, 600000 итераций; существующие корректные хеши обновляются при входе. В БД хранится только SHA-256 случайного токена сессии. Ограничены длина пароля, попытки входа/регистрации (30/IP/мин), размер WS сообщения (16 KiB), очередь доставки (256 событий) и время отправки (10 с). Logout отзывает только конкретную сессию; проверяются истёкшие сессии, действует фоновая очистка. WS сообщения не являются устойчивой очередью: после разрыва нужен follow и догрузка истории через `after_id`.

REST и WS доступны клиентам через HTTPS/WSS. Приложение доверяет forwarded headers только локальному reverse proxy по умолчанию ASP.NET. CORS закрыт по умолчанию; `MESSENGER_ALLOWED_ORIGINS` — список точных origins через запятую, включая схему и порт. Браузерные WS с неизвестным Origin отклоняются; native клиент без Origin работает. Swagger использует origin своего сервера. Логи reverse proxy должны писать `$uri`, а не `$request_uri`/`$request`, чтобы WS query-token не попадал в журнал. ASP.NET Hosting.Diagnostics с полными URL отключён ниже Warning.

## Совместимость UI

| Было → стало | Действие клиента |
| --- | --- |
| Маршруты, DTO, Bearer, client_ref, after_id → сохранены | Изменений не требуется |
| Скрыто последнее сообщение → показывается предыдущее видимое | Изменений не требуется |
| read_at списка учитывал другие чаты → рассчитывается для конкретного чата | Изменений не требуется |
| Swagger с битым `$ref` и неправильным path base → полные схемы и `/messenger` | Можно использовать для генерации клиента |
| Аватар с подходящей сигнатурой → полное декодирование PNG/JPEG/WebP, до 4096×4096 | Повреждённые файлы дают 400 `invalid_avatar` |
| Файл скачивался с недоверенным MIME → `application/octet-stream`, attachment, безопасное имя | Использовать имя/тип из AttachmentOut для отображения |
| Произвольный Origin → явный allowlist | Для браузерного клиента настроить `MESSENGER_ALLOWED_ORIGINS` |
| Неограниченное число файлов → максимум 10 за запрос, каждый до 10 МБ | Разбивать большие наборы |
| HTTP по IP → HTTPS на домене сервера | Использовать URL HTTPS из README |

## Проверки

```sh
dotnet build backend/MessengerBackend.csproj -c Release
dotnet build desktop/MessengerDesktop.csproj -c Release
dotnet build tests/ProtocolChecks/ProtocolChecks.csproj -c Release
python backend/tests/integration.py
dotnet list backend/MessengerBackend.csproj package --vulnerable --include-transitive
```

Интеграционный тест запускает изолированный сервер на временной БД v4: проверяет миграцию, старые пароли, права, валидацию, идемпотентность после правки, шифрование текста/bio/файлов, аватар, удаление, конкурентные запросы, роли, Swagger, перезапуск и потерю ключей. Запускает self-check существующего desktop-клиента и отдельные WS проверки. Последние держат 8 подписчиков, выполняют 80 HTTP запросов с параллелизмом 8, проверяют доставку 320 событий и печатают время, p50/p95, CPU и peak RSS. Это небольшой воспроизводимый smoke-нагрузочный тест, **не** гарантия ёмкости production. CI выполняет тот же сценарий на Linux.

Фактические результаты: [backend-validation.md](backend-validation.md). Для сервера предусмотрен `backend/deploy/upgrade.sh`: принимает каталог framework-dependent публикации и Git revision, останавливает сервис, сохраняет согласованную копию приложения/данных, подключает постоянные ключи и проверяет новую версию через health. При сбое автоматически возвращает старое приложение и данные. После успеха сохраняет отдельную копию ключей; дальнейшее резервирование и ротацию копий нужно включить в эксплуатационную процедуру. Пример безопасного журнала reverse proxy: `backend/deploy/nginx-messenger.conf.example`.

Ограничения: миграция шифрования и уплотнение SQLite требуют времени и свободного диска; делайте backup и проверку на копии до обновления. События не реплицируются между процессами; для нескольких экземпляров нужен другой механизм доставки. Файловая система и SQLite не образуют единую транзакцию: при аварии возможны неиспользуемые файлы. Список чатов пока возвращает весь список пользователя; историю нужно читать ограниченными страницами.
