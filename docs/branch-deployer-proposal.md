# Утилита развёртывания веток: предложение

Статус: проект решения, 24 октября 2026. Этот PR содержит только описание. Утилита, её команды, манифест и автоматическое развертывание пока не реализованы; инфраструктура сервера этим PR не меняется.

## Задача и схема работы

Оператор выбирает ветку `alex-pods/decentralized-messenger`. Утилита фиксирует её конкретный commit, собирает бэкенд и создаёт отдельное тестовое окружение с собственными процессом, БД, файлами и ключами. Один HTTPS reverse proxy направляет запросы к нужному окружению:

```text
https://preview.example.org/api/dev-<hash>/users/me
https://preview.example.org/api/feature-chats-<hash>/chats
wss://preview.example.org/api/feature-chats-<hash>/ws

nginx → отдельный внутренний порт → процесс выбранного commit
                                → отдельная БД, files, keys
```

Никакой выборки ветки внутри общего процесса API. Различные версии кода и несовместимые схемы БД сосуществуют в отдельных окружениях. Аккаунты, история и сессии между ними не общие. Пользователь desktop задаёт полный URL своего окружения; утилита не гарантирует совместимость каждого commit с клиентом.

Имя в URL — безопасный идентификатор окружения, не сырое имя Git-ветки. Ветка `feature/chats` получает читаемый slug с суффиксом из хеша полного имени. Только `[a-z0-9-]`, ограниченная длина; `feature/chats` и `feature-chats` не сталкиваются. Реестр хранит точные repository/ref/commit и постоянный environment ID, не зависящий от отображаемого slug. Slug проверяется на уникальность. Имя ветки не вставляется в shell-команду, путь, unit или nginx-конфигурацию.

Локальная проба на legacy: одновременно запущены два процесса на разных портах с префиксами `/api/feature-a-1234` и `/api/feature-b-5678` и разными SQLite/files/keys. Регистрация одного логина независимо в обеих БД прошла; токен первой БД во второй отклонён с 401. OpenAPI каждой вернул свой prefix. Существующий desktop self-check прошёл под `/api/<slug>`, включая WS, чаты, сообщения, редактирование и догрузку. Это проба настроек приложения напрямую, **не** реализация утилиты и не тест nginx для этой схемы.

На `c214733` сборка `backend-v2/Messenger.Api.csproj` сейчас заканчивается 13 ошибками компиляции в `Repositories/MessagesRepository.cs`. Swagger удалён, health и PathBase в `Program.cs` не подключены. Поэтому идея технически выполнима, но эта ветка пока не готова к автоматической публикации: утилита должна сообщить об ошибке и оставить действующее окружение без изменений. Поддержка произвольных веток без описанного контракта не обещается.

## Предлагаемый интерфейс

Только операторская CLI через SSH в MVP, без публичного HTTP API управления. Следующие команды — проект интерфейса:

```text
messenger-preview branches
messenger-preview plan --branch feature/chats
messenger-preview deploy --branch feature/chats --profile backend-v2
messenger-preview list
messenger-preview status <environment>
messenger-preview logs <environment>
messenger-preview update <environment> --commit <sha>
messenger-preview rollback <environment> --release <id>
messenger-preview stop <environment>
```

`plan` выводит ref/commit, профиль, URL, пути, лимиты и потребность в диске без запуска кода ветки. `deploy` не означает «обновлять при каждом push»: обновления явные. Удаление окружения и очистка БД — отдельные команды с явным подтверждением; `stop`, удаление ветки и истечение TTL не удаляют данные автоматически. Автоматизация через GitHub Actions — следующий этап, только с проверенной идентичностью автора и разрешённым ref, без выполнения произвольных workflow с доступом к серверу.

## Контракт ветки и адаптеры

Схема и миграции действительно принадлежат самой ветке. Утилита не генерирует общую схему и не переводит старую БД в новую автоматически. Описания таблиц недостаточно: необходим воспроизводимый способ создания и обновления БД.

Предлагается декларативный `deploy/backend.json` в ветке со следующими полями:

| Поле | Назначение |
| --- | --- |
| `contractVersion` | Поддерживаемая версия контракта |
| `profile` | Разрешённый оператором адаптер, например `legacy-dotnet8` или `backend-v2-dotnet8` |
| `project` | Относительный путь csproj внутри checkout, без `..` и выхода через symlink |
| `databaseEngine` | В MVP только SQLite |
| `databaseLineage` | Идентификатор совместимой последовательности миграций; legacy и v2 различны |
| `pathMode` | `preserve-prefix` либо `strip-prefix` |
| `healthPath`, `readinessPath` | Внутренние маршруты, таймауты задаёт оператор |
| `migrationMode` | Разрешённый адаптер миграций; не произвольная root shell-команда |

Манифест сам по себе не доверенный. Он не может выдать себе privileges, host-mounts, production-секреты, произвольные Docker arguments или неограниченные ресурсы. Для старых веток профиль и соответствие переменных задаёт оператор вне checkout. SQLite родительский каталог создаётся до запуска. SQL-файлы должны входить в publish-artifact и проверяться до переключения. Демоданные отделяются от обязательных миграций и выключаются по умолчанию: в текущей v2 `002_demo_data.sql` выполняется runner'ом как обычная миграция.

## Хранение и обновление БД

Окружение имеет отдельные state-каталоги; два окружения никогда не получают один writable volume:

```text
/srv/messenger-preview/envs/<id>/
  state.json           # операторский реестр; вне writable-доступа приложения
  releases/<sha>/      # артефакт/идентификатор образа, только чтение
  generations/<id>/db/ # SQLite вместе с WAL/SHM
  generations/<id>/files/
  generations/<id>/keys/
  backups/<id>/        # согласованный снимок БД + файлов + ключей
```

Реальные данные остаются только внутри своего окружения. По умолчанию новое окружение получает пустую БД и тестовые аккаунты, без копирования production. При новом commit той же ветки можно продолжать своё состояние только при совместимом `databaseLineage`; при смене lineage создать новое окружение либо остановиться с понятной ошибкой, не сбрасывая БД молча.

Обновление в MVP допускает короткое обслуживание: проверить свободный диск и собрать кандидат; остановить старый процесс; снять согласованный backup; создать новую generation из этого состояния; выполнить миграции и readiness на новом процессе; переключить маршрут. Параллельно снимать обычной копией активную SQLite с WAL или отдельно копировать изменяющиеся файлы нельзя. Старая и новая версии не работают одновременно на одной writable-БД.

При отказе до публикации возобновить старую generation. После приёма записей новой версией возврат старого снимка может потерять эти записи: rollback с восстановлением данных требует явного решения оператора. Просто запуск старого бинарника поверх изменённой схемы не считается откатом. Ключи сохраняются вместе с поколением; потеря ключей шифрования не исправляется новой пустой БД.

## Маршрутизация, Swagger и WebSocket

Два режима адаптера:

- `preserve-prefix`: nginx сохраняет `/api/<slug>`, приложение обрабатывает его как PathBase; этот режим проверен напрямую на legacy. Swagger servers, ссылки файлов и redirects учитывают внешний prefix.
- `strip-prefix`: nginx удаляет `/api/<slug>/`, внутренние маршруты приложения начинаются с `/`; абсолютные URL/redirects/Swagger должны явно учитывать внешний адрес. Только передать `X-Forwarded-Prefix` недостаточно, пока приложение его не обрабатывает.

Иллюстрация конфигурации для первого режима, не готовый установочный скрипт:

```nginx
# http {}:
map $http_upgrade $preview_connection { default upgrade; '' close; }

# HTTPS server {}: порт и slug берутся из проверенного реестра оператора
location = /api/feature-chats-ab12cd34 {
    return 308 /api/feature-chats-ab12cd34/;
}
location ^~ /api/feature-chats-ab12cd34/ {
    proxy_pass http://127.0.0.1:18101; # без URI: сохранить prefix
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $preview_connection;
    proxy_read_timeout 120s;
}
```

Для `strip-prefix` завершающий `/` у `proxy_pass http://127.0.0.1:18101/;` заменяет совпавшую часть URI. Поведение описано в [nginx proxy_pass](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass); требования Upgrade/Connection — в [документации WebSocket](https://nginx.org/en/docs/http/websocket.html). WS keepalive должен соответствовать таймауту. Действующие соединения при обновлении могут оборваться, клиент восстанавливает подписки и историю согласно контракту конкретной версии.

Сначала `nginx -t`, затем атомарная установка конфигурации и reload; при ошибке вернуть прежний файл. Публичные порты приложений закрыты, внешний доступ только через HTTPS-прокси. Не использовать динамический `proxy_pass` на основании произвольного URL клиента. Неизвестный slug возвращает 404. В журналах не хранить query-токены и Authorization.

## Безопасность открытого репозитория

Открытый исходный код позволяет скачать ветку, но не делает её безопасной для запуска. MSBuild, restore, migrations и само приложение выполняют произвольный код. Нельзя делать `git pull && dotnet run` от root на текущем сервере и нельзя публиковать кнопку «запустить любую ветку» без контроля доступа.

Для MVP: allowlist репозитория и веток, deploy только одобренного оператором SHA; запрещены refs из произвольных forks и неодобренных PR. Сборка — в отдельном disposable runner без SSH-ключей, production-секретов, host FS и Docker socket. Сеть сборки ограничена нужными источниками зависимостей. Артефакт передаётся как неизменяемый образ с digest и связью с SHA.

Запуск — отдельный непривилегированный контейнер на окружение, read-only rootfs, `cap-drop=ALL`, `no-new-privileges`, лимиты CPU/RAM/PIDs/диска, только свой state volume, без Docker socket/host network. Egress закрыт, кроме явно необходимых направлений; preview не имеет доступа к БД и сервисам других проектов. Привилегированный компонент только применяет заранее разрешённые шаблоны маршрутов и запуска, не выполняет команды из ветки. Для неизвестных авторов контейнеров на общем production-хосте недостаточно: нужен отдельный preview-хост/VM и отдельная политика доверия.

Пути `/api/a/` и `/api/b/` на одном домене **не изолируют браузерный origin**. HTML/SVG-вложения следует скачивать как attachment с безопасным MIME и `nosniff`; cookies, CORS и Swagger Try it out требуют проверки. Для веток с недоверенным веб-контентом предпочтительнее отдельный поддомен `<slug>.preview.example.org`; для полностью недоверенного контента — отдельный site/domain. Prefix-MVP допустим для контролируемого API с Bearer, но не обещает защиту одного preview от произвольного JavaScript другого на том же origin.

## Порядок реализации и приёмка

1. Согласовать контракт адаптера, починить сборку v2, добавить readiness и явный режим миграций. Нельзя считать TCP-listen достаточной готовностью.
2. Реализовать CLI `branches/plan/deploy/list/status/stop`, immutable SHA, безопасные slug и изолированные state-каталоги. Ограничить число одновременно работающих окружений.
3. Добавить сборку/запуск в изоляции, nginx HTTP/WS, проверку SHA и схемы, обслуживание при обновлении, backup и rollback.
4. Интеграционные тесты: две разные ветки с несовместимыми схемами; одинаковый логин и непереносимые сессии; HTTP/WS/Swagger/файлы под prefix; ошибка сборки/миграции/прокси не меняет старое окружение; сбой и возобновление; отсутствие общего writable state; slug-коллизии и инъекции; корректный restore БД/файлов/ключей.
5. Публичное включение — после проверки ресурсов и операторского доступа. На проверенном 24 октября сервере было около 375 МиБ свободного диска до локального перемещения legacy: этого мало для нескольких сборок, образов и согласованных backup. Требуются дополнительный диск/отдельный хост либо согласованная очистка. В рамках этого предложения ничего не очищается.

Legacy на действующем сервере пока остаётся работающим, его бинарники обратимо перемещены под `/opt/messenger/legacy` со ссылками по прежним путям. Данные и ключи не перемещались и не удалялись. Эта утилита должна создавать отдельные preview-окружения и не подменять текущий `/messenger` без самостоятельного решения о переходе.
