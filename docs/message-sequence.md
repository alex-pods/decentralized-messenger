# Порядок сообщений внутри чата

`id` — строковый идентификатор сообщения. Ссылки, ответы, вложения, реакции
и закрепы используют его. Порядок задаёт отдельное поле
`sequence`, начиная с 1 внутри каждого чата. Сравнивать sequence разных чатов нельзя.

Миграция `008_message_sequence.sql` выполняется штатным MigrationRunner в транзакции:

- старые сообщения получают sequence в прежнем порядке ID внутри своего чата;
- существующие данные, ID и ссылки сохраняются;
- границы прочтения переносятся в `users_chats.last_read_sequence`;
- счётчик хранится в `chats.last_message_sequence` и не уменьшается при удалении;
- триггер назначает sequence в транзакции вставки, в том числе при пересылке;
- уникальный индекс и блокировка изменения порядка защищают уже назначенные значения.

Повтор с тем же `client_ref` возвращает прежнее сообщение и sequence.
Порядок ленты, пагинация, прочтения и закрепы больше не зависят от величины ID.
Список чатов сортируется по времени последнего видимого сообщения.

## API

В объектах сообщений REST и WebSocket появилось числовое поле `sequence`.
История возвращается от меньшего sequence к большему:

```text
GET /chats/{id}/messages?limit=50&before_sequence=123
GET /chats/{id}/messages?limit=50&after_sequence=123
```

Границы исключаются; `after_sequence=0` читает с начала. Без курсора возвращаются
последние сообщения. При восстановлении соединения клиент запрашивает страницы
после последнего известного sequence и объединяет их по ID без дубликатов.

`before_id` и `after_id` принимают текущий строковый ID: они находят sequence указанного
сообщения в текущем чате. Курсор другого
чата или отсутствующей строки даёт 400. Смешивание ID- и sequence-курсоров даёт 400.

Запрос прочтения по-прежнему принимает `message_id`; сервер сам определяет его sequence.
Событие `read` сохраняет `last_read_message_id` и дополнительно передаёт
`last_read_sequence`. Граница прочтения может двигаться только вперёд.

Локальные закрепы со строковыми ID дополняются sequence из истории при открытии чата.

## Строковые ID

Сервер выдаёт пользователю 32 строчных шестнадцатеричных символа. При создании
чата клиент присылает `chat_id` из 48 таких символов. При отправке и пересылке
клиент присылает `message_id` в формате `<chat_id>.<32 случайных символа>`.
При повторном открытии личного чата для той же пары сервер возвращает его прежний ID.

`009_random_entity_ids.sql` в одной транзакции перестраивает таблицы и ссылки,
сохраняя `sequence`, зашифрованные данные, сессии и числовые ID вложений и событий.
Временные таблицы соответствий удаляются. Старый `client_ref` продолжает
проверяться по хешу исходного запроса, даже если сообщение отредактировали.

## Привязка аккаунта к серверу

Desktop отправляет случайные 32 байта в `POST /identity/proof` без пароля и токена.
Сервер отвечает открытым ключом P-256 и подписью. При первом подключении клиент
сохраняет ключ для адреса. При следующих входах, восстановлении сессии и
переподключении WebSocket проверяет свежую подпись и сохранённый ключ до отправки
секретов. Смена ключа блокирует подключение. Для удалённых адресов требуется HTTPS.
При первом входе и переезде используйте URL, полученный от администратора сервера.
Подпись подтверждает ключ, а проверка HTTPS подтверждает адрес назначения.

Сохранённая сессия содержит отпечаток SHA-256 публичного ключа. После переезда
можно изменить URL в настройках подключения и нажать «Подключить сохранённый
аккаунт». При совпадении ключа клиент обновит адрес. Старая сессия без
отпечатка привязывается при первом подключении по прежнему адресу.

Ключ подписи хранится рядом с БД в файле `<Db>.identity.key`. В Docker стандартный
путь — `/state/messenger.db.identity.key`. Путь можно задать через
`MESSENGER_SERVER_IDENTITY_KEY_FILE`. При переносе сервера сохраните этот файл вместе
с БД, вложениями и отдельным ключом шифрования данных.

## Локальная история Desktop

Клиент сохраняет полученные страницы сообщений, список чатов, участников,
закрепы и события групп в SQLite. База выбирается по отпечатку ключа сервера
и ID пользователя. При смене URL с прежним ключом используется та же база.
Полученные данные шифруются AES-GCM. На Windows ключ хранится под защитой DPAPI
текущего пользователя. На Linux и macOS файл ключа доступен владельцу.

При обрыве связи в открытой сессии доступны ранее полученные страницы и переход
по сохранённым ссылкам. При запуске приложения требуется подтверждённая сервером
сессия. После восстановления WebSocket клиент сверяет уже открытую часть истории
по `sequence`, затем догружает новые сообщения. Ответ 403 или 404 исключает
показ локальной копии чата. Файлы вложений загружаются с сервера по запросу,
локально сохраняются только их метаданные.

Личные закрепы со строковыми ID импортируются один раз из файлов старых
адресов, привязанных к тому же ключу.

### Перенос числовых закрепов

До перехода на строковые ID соберите каталоги `messenger-desktop/pins` со
старых устройств и резервную копию SQLite до миграции 009. Утилита читает
оригиналы, мигрирует отдельную копию БД и конвертирует закрепы по временным
таблицам внутри 009. Для пропущенных удалённых или недоступных сообщений и
дублей выводится счётчик.

```powershell
python tools/migrate-legacy-pins.py --db ../backup.db --legacy-address https://old.example/api/dev --address https://current.example/api/dev --pins ../device-a-pins --pins ../device-b-pins --out ../converted
```

Если URL не менялся, достаточно `--legacy-address` с тем адресом, который был
указан в старом Desktop. `--address` задаёт точный URL нового клиента.
Перед переносом рабочей базы остановите запись и сделайте свежую копию.
Для запуска используйте `converted/messenger.db` вместе с исходными вложениями
и ключами сервера. Файлы из `converted/pins/device-N` перенесите на
соответствующее устройство в `messenger-desktop/pins/migrated-numeric` в каталоге
данных приложения. При входе Desktop один раз импортирует их для
проверенного сервера и нужного аккаунта. Оригиналы остаются на своих местах.

Файлы закрепов содержат локальные выдержки текста. Передавайте только файлы
нужного устройства его владельцу. Новые ID в файлах соответствуют именно
БД из того же запуска утилиты. Если база уже прошла 009, для переноса нужна
резервная копия до 009 и повторный переход с этой копии.

## Отправка без хранения содержимого

В Desktop молния рядом с кнопкой отправки включает режим для одного сообщения.
Черновик запоминает режим при переключении между чатами, при ошибке отправки
режим сохраняется. После успешной отправки следующий черновик возвращается к
обычному режиму. Сообщения с отметкой «без хранения» остаются в памяти текущей
сессии Desktop.

Сервер сообщает о поддержке через `GET /capabilities` (`message_relay: true`).
Клиент отправляет `POST /chats/{chat_id}/messages/relay` с полями
`message_id` и `text`. Текст передаётся событием `message_relayed` только
подключённым участникам, которые подписались на чат и объявили поддержку
заголовком `Messenger-Message-Relay: 1` при подключении WebSocket.
Сервер проверяет членство и применяет общий антифлуд.

Миграция 010 добавляет таблицу квитанций. В ней хранятся ID сообщения, чата и
отправителя, `sequence`, время отправки и число соединений, в чью очередь
попало событие. Текст и производные от текста данные на диск не записываются.
Квитанция `202` подтверждает постановку события в очередь, а повтор успешного
запроса с прежним ID возвращает ту же квитанцию без повторной передачи.
Если получателей нет, запрос возвращает `relay_no_recipient` и его можно
повторить. Если результат передачи неизвестен, сервер возвращает
`relay_delivery_unknown` и сохраняет резерв ID, чтобы избежать повторной отправки.

У офлайн-участников такое сообщение в истории не появится. Вложения, ответы,
редактирование, реакции, пересылка и закрепление доступны для обычных сообщений.
Последующие сохранённые сообщения продолжают тот же счётчик `sequence`.

## Проверка и запуск

Перед первым запуском обновлённого сервера сохраните резервную копию БД.
Для живой SQLite используйте backup API или остановите сервер перед копированием.
Обновлённый клиент запускайте вместе с обновлённым сервером: форматы ID REST и
WebSocket изменились.

Из корня проекта:

```powershell
python tests/message_sequence.py --ui --migration-source путь-к-копии.db --out ../sequence-check
python tests/legacy_pins_migration.py --migration-source путь-к-копии.db
dotnet run --project tests/ServerIdentityChecks -c Release
```

Папка результатов должна быть новой. Исходная БД открывается только для чтения;
миграция проверяется на копии. HTTP и GUI работают с отдельной временной базой.
Тест включает параллельные отправки, повторы, искусственно переставленные ID,
историю с обоими видами курсоров, прочтения, ответы, закрепы, пересылки, удаления,
обрыв WebSocket и восстановление истории. Снимки GUI сохраняются в папке результатов.
