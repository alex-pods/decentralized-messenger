# Порядок сообщений внутри чата

`id` остаётся числовым идентификатором сообщения. Ссылки, ответы, вложения,
реакции и закрепы продолжают использовать его. Порядок задаёт отдельное поле
`sequence`, начиная с 1 внутри каждого чата. Сравнивать sequence разных чатов нельзя.

Миграция `008_message_sequence.sql` выполняется штатным MigrationRunner в транзакции:

- старые сообщения получают sequence в прежнем порядке ID внутри своего чата;
- существующие данные, ID и ссылки сохраняются;
- границы прочтения переносятся в `users_chats.last_read_sequence`;
- счётчик хранится в `chats.last_message_sequence` и не уменьшается при удалении;
- триггер назначает sequence в транзакции вставки, в том числе при пересылке;
- уникальный индекс и блокировка изменения порядка защищают уже назначенные значения.

Повтор с тем же `client_ref` возвращает прежнее сообщение и sequence.
Порядок ленты, пагинация, прочтения и закрепы больше не зависят от величины ID.
Список чатов сортируется по времени последнего видимого сообщения.

## API

В объектах сообщений REST и WebSocket появилось числовое поле `sequence`.
История возвращается от меньшего sequence к большему:

```text
GET /chats/{id}/messages?limit=50&before_sequence=123
GET /chats/{id}/messages?limit=50&after_sequence=123
```

Границы исключаются; `after_sequence=0` читает с начала. Без курсора возвращаются
последние сообщения. При восстановлении соединения клиент запрашивает страницы
после последнего известного sequence и объединяет их по ID без дубликатов.

Старые `before_id` и `after_id` сохранены: они находят sequence указанного сообщения
в текущем чате. Это ID существующей строки, а не число для арифметики. Курсор другого
чата или отсутствующей строки даёт 400. Смешивание ID- и sequence-курсоров даёт 400.

Запрос прочтения по-прежнему принимает `message_id`; сервер сам определяет его sequence.
Событие `read` сохраняет `last_read_message_id` и дополнительно передаёт
`last_read_sequence`. Граница прочтения может двигаться только вперёд.

Локальные закрепы дополняются sequence; старые JSON-файлы обновляются при открытии чата.
Для старого закрепа вне загруженного окна клиент один раз просматривает страницы истории.
Недоступные старые закрепы сохраняются без известного порядка (sequence 0).

## Проверка и запуск

Перед первым запуском обновлённого сервера сохраните резервную копию БД.
Для живой SQLite используйте backup API или остановите сервер перед копированием.
Обновлённый клиент запускайте вместе с обновлённым сервером: старый сервер не передаёт sequence.
Ключи сервера, строковые ID и передача сообщений без сохранения в этот этап не входят.

Из корня проекта:

```powershell
python tests/message_sequence.py --ui --migration-source backend/scroll-test.db --out ../sequence-check
```

Папка результатов должна быть новой. Исходная БД открывается только для чтения;
миграция проверяется на копии. HTTP и GUI работают с отдельной временной базой.
Тест включает параллельные отправки, повторы, искусственно переставленные ID,
историю с обоими видами курсоров, прочтения, ответы, закрепы, пересылки, удаления,
обрыв WebSocket и восстановление истории. Снимки GUI сохраняются в папке результатов.
