# Preview CLI

Оператор выбирает ветку; CLI скачивает её **с GitHub**, фиксирует commit, собирает `linux-x64` на машине оператора и передаёт архив на Linux-хост. На сервере исходники и сборка временно лежат в `/opt/messenger-preview/<id>`. Каждый процесс имеет свой внутренний порт, публичный `/api/<id>/` и отдельное состояние.

`stop` останавливает процесс, удаляет исходники, сборку и systemd unit. Публичный маршрут отвечает 503. **БД, вложения, ключи и запись окружения сохраняются** в systemd StateDirectory `/var/lib/messenger-preview-<id>` (при DynamicUser физический каталог может быть в `/var/lib/private`). Это не команда удаления переписки. Повторный deploy того же commit восстанавливает окружение с прежними данными.

## Требования

- Машина сборки: Python 3.10+, Git, .NET 8 SDK или новее, `ssh` и `scp`; Linux или Windows.
- Сервер: Python 3, nginx, systemd, ASP.NET Core 8 runtime, авторизованный root-доступ по SSH. `install` и deploy имеют доступ администратора — не предоставляйте эту CLI анонимным пользователям.
- Код ветки при сборке выполняется с правами локального пользователя. `--accept-build` означает явное разрешение запускать **проверенный код**. Для недоверенных PR/forks используйте отдельную disposable VM/runner без секретов. Публичный исходный код не является признаком доверия.
- SDK и Docker SDK-image на сервер не устанавливаются. Свободное место проверяется до распаковки; максимум два preview, лимиты процесса: 192 МиБ RAM, 50% CPU, 64 задачи. Это ограничения, а не гарантия доступной ёмкости хоста.

## Команды

Из корня репозитория:

```sh
# Явная однократная установка/обновление агента и include в существующий nginx site.
python tools/preview/preview.py --host root@176.53.160.4 install \
  --base-url https://sftp-ftp-server.duckdns.org \
  --nginx-site /etc/nginx/sites-available/SFTPServerBackend

python tools/preview/preview.py --host root@176.53.160.4 branches
python tools/preview/preview.py --host root@176.53.160.4 deploy --branch dev --profile legacy --accept-build
python tools/preview/preview.py --host root@176.53.160.4 list
python tools/preview/preview.py --host root@176.53.160.4 status dev-ef260e9aa3c6
python tools/preview/preview.py --host root@176.53.160.4 logs dev-ef260e9aa3c6
python tools/preview/preview.py --host root@176.53.160.4 stop dev-ef260e9aa3c6
```

В PowerShell многострочные команды можно записать одной строкой. ID и URL возвращаются deploy/list; пример для dev получается из имени и первых 12 цифр SHA-256 имени ветки. Локальный checkout и временные пакеты удаляются после выполнения CLI, серверный пакет — после установки, серверный checkout/publish — при `stop`. Скачивание и установка агента происходят явно командой `install`, деплой произвольной ветки его не обновляет.

## Ограничения первой реализации

- Работает профиль legacy: `backend/MessengerBackend.csproj` либо `backend-legacy/MessengerBackend.csproj`, настройки `MESSENGER_*`. Актуальная `dev` содержит первый вариант.
- `--profile v2` позволяет проверить локальную сборку, но агент намеренно откажется публиковать её до исправления сборки/readiness/PathBase. Утилита не чинит код выбранной ветки.
- Повторный запуск разрешён только того же commit: новый commit при сохранённом состоянии требует отдельной процедуры миграции. Обновления, backup/rollback схем, произвольный манифест и удаление state ещё не реализованы. Все SQL и миграции берутся из выбранного commit, state между ветками не копируется.
- Запущенное окружение не перезаписывается: сначала `stop`. Новые исходники скачиваются заново; исчезнувшую upstream-ветку автоматически восстановить нельзя, хотя состояние на сервере сохранено.
- Процессы не включаются в автозапуск после reboot. `status` дополнительно читает фактическое состояние systemd, даже если реестр содержит последнюю запись running. После reboot используйте stop/deploy.
- Контролируемые процессы изолированы DynamicUser, read-only системной FS, собственными state и лимитами. Им разрешён loopback, поэтому это **не sandbox для враждебного кода**: нельзя размещать непроверенные ветки на хосте с чужими внутренними сервисами. Контейнеры/отдельная VM из полного предложения — дальнейшая работа.
- Разные пути одного домена остаются одним browser origin. Для API это допустимо при проверенном коде; для недоверенного HTML нужны отдельные поддомены/домены. Предварительная аутентификация preview на уровне прокси не добавлена; тестовый API доступен по возвращённому URL и использует собственную авторизацию бэкенда.
- TTL и чистка данных не реализованы. Из старого production ничего не удаляется. Существующий `/messenger` и его сервис не меняются.

## Проверки

```sh
python -m unittest discover -s tools/preview -v
```

Тесты проверяют имена, отсутствие shell-инъекций в SSH host, архивы с traversal/symlink, сохранение state при очистке кода, идемпотентный stop, откат nginx и запрет неявного обновления БД. Фактический цикл deploy → stop → deploy с сохранением аккаунта проверяется отдельно на тестовом окружении, не на production-БД.
